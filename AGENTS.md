## 1. What this project is

**Exiva XP is a personal Tibia character intelligence hub for Night'Flyn** (Elder Druid, Gentebra) — private-first, with optional public features later. It centralises: Hunting Analyser sessions, XP and highscore history, profit, deaths, stamina planning, hunting places, creature data, elemental weaknesses, charms, and long-term progression. Every tool must answer a practical question about the character: *where should I hunt, which element is best, how much profit do I make, how does my XP evolve, which respawns fit my level, which creatures do I kill most, which charms matter, how does my performance change.*

The community hunting database is the planning engine underneath, not the product. The character is the centre.

**The only reference projects** (never add others without owner approval):
1. Exiva XP itself — https://nesleykent.github.io/exiva-xp/index.html
2. TibiaTools — https://tibiatools.io (damage/combat calculator logic: resistances, mitigation, crit, fatal, charms)
3. Respawn Finder — https://github.com/danyelvarejao/respawn-finder (respawn search patterns used to improve the hunting planner/database; do not add item timers, party split or blessing tools unless the owner explicitly asks)
4. Tibia XP History — https://github.com/mathiasbynens/tibia-xp-history (daily progression tracking; its formulas, crawl mechanism and 03:00 UTC schedule are ported, while row dates follow Tibia's 10:00 Europe/Berlin server-save day)

## 2. Architecture (do not deviate)

- **Plain HTML5 + CSS + vanilla JS ES modules. No frameworks. No build step. No npm dependencies. No TypeScript.** The site deploys to GitHub Pages as-is; the only deploy-time transform is the cache-stamp sed in `publish.yml`.
- **Thin HTML pages, one JS controller each.** Every `*.html` is a shell (head, `#rail`, `#stage`, one `<script type="module" src="assets/js/pages/X.js">`). All rendering happens in the controller.
- **The engine directory is DOM-free and Node-safe.** `assets/js/engine/*` runs identically in the browser and in Node inside Actions. The pipeline must never disagree with what the browser shows. Never import DOM APIs there.
- **Layers, strictly:** `lib/` (primitives: fmt, text, stats) → `engine/` (game logic) → `data/sources.js` (loaders + backends) → `viz/` (SVG builders) → `shell.js` (chrome + shared fragments) → `pages/` (controllers). Lower layers never import higher ones.
- **Data is generated by pipeline scripts, committed to `data/`, served statically.** Browser code never writes to `data/`; the personal logbook lives in `localStorage` (`exiva:logbook`).
- **`BACKEND = 'browser'`** — private-first: pages read hunt evidence from the local logbook. GitHub Issues/Discussions remain available as *optional* sharing backends. Do not flip the default without owner approval.

## 3. Philosophy and design principles

1. **Invent nothing.** Derive what arithmetic allows; when a number cannot be known, show "—" or ask the user for it. Never fabricate formulas, mechanics, or data. Every game mechanic must trace to TibiaWiki, TibiaData, the Cyclopedia exports, or the user's own input. (Violations already caught and removed: a fabricated "Major charms need level 250+" claim; a damage formula deriving min/max from level+skill; a tracker branch that copied yesterday's skill value into today's entry.)
2. **Honest data lineage.** Generated data carries its source (`source` markers, `wikiUrl` links, "unverified" caveats). A failed measurement is `null`, never a carried-forward value. History entries must satisfy the XP formulas (smoke-tested).
3. **Verify, don't assume.** Every change is checked in the browser preview and by `node pipeline/smoke.mjs` before commit. Every deploy is watched to completion and spot-checked live.
4. **The character is the centre.** New features must answer one of the practical questions in §1. Community/public features are optional extras, never the default surface.
5. **Small, boring, consistent.** No abstractions until the third use. No new files when an existing layer fits. Match the file's existing idiom.

## 4. Coding standards

- ES modules, single quotes, semicolons, 2-space indent, trailing commas in multiline literals.
- JSDoc block comment at the top of every file saying what it is; inline comments only for constraints the code can't express (never narration of the next line).
- CSS: compact one-line declarations per rule (match the existing files); design tokens only — never hardcode a colour, radius, spacing, or font that has a token (`--surface`, `--ink`, `--blue`, `--s*`, `--r-*`, `--t-*`, `--e-*`).
- Naming: camelCase functions/variables, SCREAMING_SNAKE for module constants, kebab-case files, semantic CSS class names by meaning not colour (`pill-success`, not `pill-green`).
- Vocabulary (post-pivot, fully renamed — keep consistent): hunt evidence basis is `curated | blended | logged` (never "community"); the shared dataset is `data/shared-hunts.json`; pages say "save"/"log", not "publish"/"submit to the community".
- Node scripts (`pipeline/*.mjs`): plain Node 22, no dependencies, `node:` prefixed imports, graceful no-op exits for already-done work, retry with backoff for flaky upstreams (TibiaData dev instance 429s and 5xxs).
- OWNER RULE (non-negotiable): every commit — human, agent or workflow — is authored as `nesleykent` (`20923096+nesleykent@users.noreply.github.com` for workflows, the owner's own email locally). The contributor list shows the owner alone. Never invent a noreply address, never use another bot identity, and never add agent/bot `Co-Authored-By:` trailers.

## 5. UI rules (Instagram Design System)

The interface follows the reverse-engineered Instagram Design System (see README "Design system adherence" for the audit history). Non-negotiables:

- **Shell:** desktop sidebar → narrow icon rail → mobile bottom tab bar (≤700px). GitHub + appearance toggle live in a floating top-right cluster on mobile, never in the tab bar. **The tab bar holds exactly 5 destinations** (Home, Character, Planner, Tools, Log a hunt — the daily loop; Instagram keeps five too); the other pages are desktop-sidebar + home-workspace only, marked by the NAV entries' 4th field (`mobile`) and hidden via `.rail-desktop-only`. Never add a 6th mobile tab without owner approval; verify at 320px whenever NAV changes.
- **Colour:** near-monochrome; one signature blue `#0095F6` for primary actions; the brand gradient only as whole-surface/whole-word treatment (`grad-text`), never a small accent. Element colours (`--c-*`) are *data* colours: meters, badge tint washes — never component chrome, borders, or icon tints.
- **Components:** `.btn` tiers primary/secondary/tertiary/destructive, flat 6px radius, letter-spacing -0.01em, disabled opacity .3. Two chip species, never conflated: `.badge` is the source Badge verbatim (solid tone fill, white 11px/700 uppercase, 4px radius) for genuine STATUS indicators only — basis (Curated/Logged/Blended), rules-check (Faulted/Flagged/Clean), evidence provenance; tones success/info/error are source colours, warning is the brand orange stop (documented extension — the source has no caution tone). `.pill` is Exiva's own quiet data/label chip (soft wash, ink text, pill radius) for categorical metadata and element readouts — element colours tint pill washes only, never badge fills. There is NO bordered Tag component in use — the source's Tag is an interactive filter chip this app doesn't have. `.panel` cards at 6px radius, hover-only shadow; art tiles at 12px (editorial variant).
- **Sort controls** use `sortMenu()`/`bindSortMenu()` from shell.js (anchored menu with checkmark, Apple HIG pattern) — never a native `<select>` for sort. Filter fields use `.lbl` + `.filter-bar` with the mobile collapse (`.filter-toggle`/`.filter-more`).
- **Mobile filter bars must not be sticky** (iOS Safari sticky+backdrop-filter ghosting bug — documented in pages.css).
- Light-first with dark appearance via `data-appearance`; both must be checked for contrast when touching colours.

## 6. Implementation patterns

- New page = new `X.html` shell copied from an existing one + `assets/js/pages/X.js` controller booting via `boot('X.html', { ledger })` + NAV entry in shell.js (check 320px tab bar) + README pages-table row.
- Data loaders live in `sources.js`'s `FILES` map — **all data fetches go through it** (the deploy stamp seds that map for cache busting; a fetch outside it silently serves stale data).
- Charts: `bars()`/`flow()` from `viz/svg.js` — extend those, don't add chart libraries.
- Formulas: `engine/progression.js` (XP/level, base value — ported from tibia-xp-history) and `engine/planning.js` (stamina, profit, effective damage multipliers). New game math goes in engine with a source link and a smoke assertion.
- Character tracking: `pipeline/track-character.mjs` crawls TibiaData dev-instance highscores (the only public exact-XP source), same-day refreshes are allowed (highscores roll during the day), a page-1 snapshot guards staleness, and reruns no-op cleanly. Never write the snapshot before the run fully succeeds.
- Online tracking: `pipeline/track-online.mjs` polls TibiaData's world endpoint every 15 minutes via `.github/workflows/track-online.yml` and records whether Night'Flyn appears in Gentebra's `online_players` list. This creates sampled status only; never backfill or invent online history.
- Cache busting: `publish.yml` stamps `?v=<sha>` into HTML asset tags, JS import specifiers, and the `FILES` data map at deploy time. Source files stay unstamped locally — never hand-write a `?v=` in the repo.

## 7. Forbidden changes

- No frameworks, bundlers, package.json, node_modules, or TypeScript.
- No invented game mechanics or formulas (see §3.1). No placeholder/fake data presented as real.
- No renaming datasets, basis vocabulary, or public URLs without a full-codebase consistency sweep AND owner approval (the community→logged sweep is done; don't churn it again).
- No touching `data/bestiary.json`, `data/grounds.json`, `data/charms.json` by hand — they are exports/curated inputs.
- No always-on card shadows, no colour-named CSS classes, no native sort `<select>`, no emoji in UI chrome, no new colour accents outside the token set.
- No sticky+backdrop-filter on mobile. No nav additions without the 320px check.
- Do not commit directly to `main` without running `node pipeline/smoke.mjs` and `node --check` on every touched JS file.
- Do not change the tracker's schedule, its no-op semantics, or history-entry shape without migrating the existing 31+ days of data.
